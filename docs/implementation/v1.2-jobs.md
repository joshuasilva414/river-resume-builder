# River v1.2 jobs and wording

Implementation follows the [approved plan](v1.2-plan.md) and [Paper handoff](v1.2-paper.md). Paper designs were handed off as Designed with inspected screenshots before UI changes: `BIP-0` (URL/paste and editable review), `BKS-0` (recovery), `BK8-0`/`BKG-0` (qualifications/eligibility), `BMG-0` (matching actions), and `BMQ-0`/`BMZ-0` (editable wording and bulk actions).

## Import and reviewed refresh

`JobImport` is the single primary job-creation action. Users select Public URL or Paste text and choose a personal model before execution. `job_imports` stores the input, selected profile, retained text, analysis, current operation and save identity. `JOB_AI_WORKFLOW` also dispatches `job-import` operations. Existing operation concurrency, cancellation and reconciliation apply. The UI polls operation stages and provides Cancel. Cancelling a still-submitting request cancels its resulting operation as soon as its identity arrives.

Retrieval checks the public HTTP(S) destination, credentials, normalized IP literals, custom ports and local names. DNS A/AAAA answers must all be public. Ordinary retrieval uses manual redirects and checks each new destination, up to five redirects. The response stream is bounded to 2 MiB, extracted text to 120,000 characters, and the retrieval attempt to 30 seconds. Browser rendering is reserved for incomplete or JavaScript pages. Browser resource requests are limited to the validated origin and up to seven validated script origins; media, styles, fonts and sockets are excluded. The browser navigation timeout is 15 seconds. Browser response metadata and redirect destinations are checked before retaining text.

The implementation uses the current [Cloudflare content quick action](https://developers.cloudflare.com/browser-run/quick-actions/content-endpoint/) through `BROWSER.quickAction("content", options)`. Installed Workers types specify `BrowserRunContentOptions` and a JSON response containing `success`, `result`, and `meta`; the adapter validates that envelope. It does not interpret the response as raw HTML. Retrieved HTML becomes plain text and is passed to the selected provider as untrusted data. No user credentials or cookies are forwarded to the posting site.

Blocked, login-only, incomplete, oversized, or failed retrieval offers paste/retry. Retained text survives provider failure. Retries are bounded to three attempts and reuse that retained text. Cancelled or obsolete operations cannot publish analysis. The save transaction also rejects cancelled, running, already-saved or foreign import records. Users may explicitly continue manually with retained text.

One review edits the description, employer/title/location and requirement rows. Select all counts the complete result set across ten-row pages. Saving commits the job, immutable posting capture, requirements, reference rows, receipt and audit together. Refresh is explicit and writes a new capture. Earlier captures, requirement versions and saved résumé references remain available. Replaying the save returns its established result; another save key cannot duplicate the same import.

Endpoints:

- `POST /api/v1/jobs/imports`: start retrieval and analysis.
- `GET /api/v1/jobs/imports/:importId`: inspect retained text, editable analysis and execution status.
- `POST /api/v1/jobs/imports/:importId`: retry a failed/cancelled import with its observed revision.
- `POST /api/v1/jobs`: `JobCommand` with `type: "import"` saves reviewed data, with an optional existing job target for refresh.
- Existing operation cancellation remains shared. Personal AI processing remains account-owner-only.

Migration `0036_v1_2_jobs.sql` adds only `job_imports` and its owner index. Existing snapshots and stored requirements do not need destructive conversion.

## Qualifications, matching and stale results

Requirements optionally carry `kind: Qualification | Eligibility`; older rows without a kind remain qualifications. New import output requires an explicit kind. Eligibility covers posting conditions such as authorization and citizenship. It has a separate informational view, never receives evidence matches, and never supplies inferred personal answers or a résumé-creation gate. Changing an existing qualification into eligibility removes its current evidence associations while retaining prior workspace versions.

Requirement extraction supports 100 items and retains source passages internally. Ordinary views omit confidence, passage controls, evidence verification status and provenance identifiers. Current AI result review offers Use selected and Use all for requirements and matches. Selected requirements merge with current unselected requirements; all requirements replaces the reviewed map after acknowledging any removed associations. Match acceptance inserts all chosen associations in the same guarded transaction as its review decision. Duplicate/foreign result identities and stale batches fail before any write.

Pending job analysis compares the immutable posting identity and relevant requirement content. It ignores job display edits and selection-only revisions. Ranking ignores eligibility-only changes and evidence metadata-only revisions; evidence content and lifecycle changes remain relevant. Acceptance reads the current workspace before applying changes and guards its actual revision to preserve intervening unrelated changes. Accepted/rejected records no longer compare themselves with pre-acceptance inputs and do not show false stale warnings.

## Wording and recoverable deletion

Single wording choices are editable before Apply. The queue offers editable choices, Apply selected and Apply all, with complete-set counts across ten-row pages. One batch permits one choice per entry; competing alternatives for the same entry cause an explicit conflict. The batch validates every proposal, original target, current résumé, supporting evidence and context before writing one résumé revision. Guard identities are encoded in bounded JSON parameters so a larger batch does not exhaust D1's bound-parameter limit. A successful retry returns the original receipt.

The editor integrates bulk application with its existing serialized external-edit path and one undo state. Accepted wording no longer shows stale warnings caused by its own override. Manual wording editing and job deletion no longer require rationales. Job detail uses the shared Trash action and workspace Undo feedback. Jobs can be restored without losing captures, requirements or selections.

### Structured wording

`wording-structured.ts` adds a real `structured-field` path alongside legacy content placements. Paths identify a section, optional legacy block container, nested record identities, stable field identity, and optional text-list position. The target captures field purpose, text, selected typed evidence references, the container's saved reference, and list length. Entry reordering, compatible layout switches, draft names, and sibling wording do not invalidate an unchanged target. Target edits, removed records, incompatible fields, changed support, or changed list shape require fresh review.

Direct Summary text and nested accomplishments use the existing generation, cancellation, provider output validation, single review, and selected/all batch transaction. The v2 wording profile supports structured targets; v1 profiles and historical inputs remain readable. The evidence bound now matches structured content's 200 references, with the existing explicit 160,000-character complete-input limit. No source or result is silently truncated. Applying a field edit preserves other values, nested records, layouts, and shared evidence references. An internal local-edit marker satisfies composition validation without asking for a user rationale.

`StructuredWording` sits beside the section or entry editor and uses the same wording choices panel. It enumerates nonempty text values and text-list items, excluding headings and non-text fields. It does not project schema values into fake legacy placements. Manual field edits and accepted suggestions retain the editor's Undo behavior. Scoped Undo preserves intervening sibling edits and refuses a target that has subsequently changed.

### Bounded release audit

The follow-up audit corrected a batch guard that collapsed different observed revisions of the same context. Every observed context revision now participates in the atomic check, so a newer choice cannot hide an older choice's stale context. Bulk controls count only choices still present after refresh, reject competing alternatives before dispatch, retain a direct review/regenerate action for each choice, and refresh saved state after an uncertain apply response. The structured fixture now uses the domain `Composition` type, including its readonly sections.

Intentional repeated job imports receive a fresh request identity after a successful start; failed requests retain their replay identity. Retry uses the observed import identity and revision. Retrieval now fails closed on either DNS-family error, malformed IPv6 answers and deprecated relay addresses, enforces exact response media types and browser redirect limits, and registers cancellation before browser dispatch. A deadline during script-origin validation prevents a late browser launch. Evidence labels describe whether a suggestion uses a reference; they do not imply that shared structured references were deleted.

The focused `job-import` and `wording` Workers suites pass 25 tests. New cases cover mixed context revisions, DNS failures, pre-dispatch cancellation, pending-browser deadlines, excessive redirects and streamed size bounds. The web TypeScript check passes. These tests use mocked network/browser responses: application DNS preflight is not connection-level address pinning, and the fetch/browser APIs resolve their connections independently. Hosted network behavior, provider acceptance and browser UI acceptance remain part of the parent's release verification.
