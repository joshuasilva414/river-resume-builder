## Exact graph and lifecycle

Each design has an aggregate revision and a selected Document, Section, or Block editing scope. Its immutable revisions capture all fourteen components: one Document, six Sections, and seven Blocks. Saving changes only the selected component. Manual edits and explicit component combinations create Draft graphs. Revision races roll back the complete graph, head, audit, reference indexes, and permanent receipt together.

Built-in Classic, Minimal, and Technical remain fixed revision 1. New donors must be built-in graphs or exact Approved custom revisions. Combinations retain donor component digests and identities and undergo their own validation. Retirement does not rewrite captured components. A stale manual save retains its local form; explicit reload or a separately named Draft from the captured base are available.

`river-template-graph-v1` validates the complete declared structure, child slots, allowed font resources, closed LaTeX grammar, and scoped style overrides. Font and body size inherit at every level. Section spacing is available on Documents and Sections; margin is Document-only. Permitted values are the typed manifest values. Scalars remain escaped. The compositor applies the resolved overrides, including 9 pt body text.

Custom graphs use `river-tectonic-0.3.0`; fixed pack identities retain `river-tectonic-0.2.0`. Historical fixed checkpoints do not silently acquire a new renderer identity.

## Validation and artifacts

A validation command persists its Operation and dispatch before invoking `TemplateValidationWorkflow`. One template validation may be active per Owner. Each immutable Draft revision has at most three validation attempts. Each of four canonical fixtures renders twice, with one bounded Workflow retry and a four-minute step timeout. Individual runtime jobs retain the existing document service bounds.

`river-template-fixtures-v1` covers all seven content types, Unicode/special characters, long page flow, and repeated text/reading order. Fixture placement IDs are deterministic at construction; no random generation occurs during Worker module initialization. Fixture inputs never query Owner evidence or résumé storage.

Per-fixture publication follows immutable private R2 writes. Retries verify existing bytes. Results pin the graph digest, fixture-set digest, renderer, validator, compiler, font/bundle resources, text report, and both output fingerprints. Interrupted results remain inspectable; cancellation rejects late publication. Complete validation requires all fixtures, exact identities, passing text checks, and deterministic fingerprints. Approval separately requires the exact successful report and an initially unchecked visual-review acknowledgment. This does not confer ATS Screener tested status.

The library's public built-in PDF examples contain canonical synthetic content only. They were generated by the pinned offline document fixture runner. Custom fixture PDF, LaTeX, text, and report downloads require the Owner session and a validation owned by that account.

## Résumé bindings

A new binding uses `{designId, revisionId}` and an atomic Approved-state guard. The working draft reference index is updated with its aggregate and audit. Existing unchanged retired bindings remain renderable. New branches require an eligible explicit binding. Saving another template revision cannot update existing bindings.

Preview operations capture the exact custom graph. Checkpoints retain that full graph alongside the exact saved composition, contact values, evidence, template identity, and generated artifacts. Retried checkpoints use their captured graph. The last successful preview remains visible while a new binding renders.
